# DuckDBとBigQueryにおけるdbt testの実行記録

[English](./README.md)

## 概要

このディレクトリには、同じdbtデータテスト群をDuckDBとBigQueryで実行した際の記録を掲載しています。

この記録の目的は、ポートフォリオプロジェクト
[`access-governance-warehouse`](../../../README.md)
の開発中に得られた観察を、実行条件と制約を含めて残すことです。

DuckDBとBigQueryの一般的な性能を比較するベンチマークを目的としたものではありません。

## 背景

このプロジェクトでは、次の2つの実行ターゲットを使用しています。

- ローカルでの開発および検証に使用するDuckDB
- クラウドデータウェアハウス（cloud data warehouse）上での実行に使用するBigQuery

開発中、多数の小さなdbtデータテストを実行した際に、2つのターゲット間で実行時間に大きな差があることを観察しました。

この観察を記録するため、両方の環境で同じ315件のデータテストを5スレッドで実行しました。

## 実行コマンド

### BigQuery

```bash
uv run dbt test --target bigquery_dev
```

### DuckDB

```bash
uv run dbt test
```

## 実行条件

| 項目 | BigQuery | DuckDB |
|---|---|---|
| dbt Core | 1.11.8 | 1.11.8 |
| アダプター | dbt-bigquery 1.11.1 | dbt-duckdb 1.10.1 |
| データテスト数 | 315 | 315 |
| スレッド数 | 5 | 5 |
| 成功 | 315 | 315 |
| 警告 | 0 | 0 |
| エラー | 0 | 0 |
| スキップ | 0 | 0 |

テストには、このポートフォリオプロジェクトで使用している小規模な合成データを使用しました。

## 記録された結果

| ターゲット | 実行時間 |
|---|---:|
| DuckDB | 6.97秒 |
| BigQuery | 58.80秒 |

この一組の実行記録では、BigQueryターゲットの実行時間はDuckDBターゲットの約8.4倍でした。

実行時間の差は51.83秒です。

## 観察された実行傾向

ログ上では、多くの個別テストが、おおむね次の時間で完了していました。

| ターゲット | 多くの個別テストのおおよその実行時間 |
|---|---:|
| DuckDB | 0.07～0.12秒 |
| BigQuery | 0.6～1.3秒 |

一部のテストは、この範囲外の実行時間となっています。

この記録からは、今回のワークロードでは、多数の小さなテストクエリを実行する際の時間差が積み重なり、全体の実行時間に大きな差として表れたことを確認できます。

ただし、ログだけでは、それぞれの要因が実行時間差にどの程度寄与したかは判断できません。

影響した可能性がある要因には、次のものがあります。

- リモートサービスへのクエリ送信
- ネットワーク通信
- 認証およびAPI通信
- クエリのスケジューリング
- 分散クエリ実行
- ストレージへのアクセス
- アダプター固有の処理
- キャッシュの状態

これらは仮説であり、この実行記録では個別に分離または測定していません。

## 結果の解釈

この記録によって確認できるのは、次の限定的な事実です。

> このポートフォリオプロジェクトにおける1回の実行記録では、315件のdbtデータテストを5スレッドで実行した際、BigQueryでは58.80秒、DuckDBでは6.97秒を要した。

一方、この記録から次のような一般的結論を導くことはできません。

- BigQueryは一般にDuckDBより遅い。
- 他のワークロードでもBigQueryは約8.4倍遅い。
- 実行時間差は固定的なクエリオーバーヘッドだけで生じた。
- 本番の分析ワークロードではDuckDBの方が適している。
- データ量やクエリの複雑性が増えても同じ結果になる。

DuckDBとBigQueryは、アーキテクチャと想定される利用環境が異なります。

DuckDBはアプリケーションプロセス内でローカルにクエリを実行します。一方、BigQueryはリモートサービスを通してクエリを受け付け、分散環境で実行するクラウドデータウェアハウスです。

小規模な合成データに対して多数の小さなテストクエリを実行した結果を、大規模なデータ走査、複雑な変換、同時実行を伴うワークロード、本番運用へ一般化することはできません。

## 制約

この記録には、次の制約があります。

- 各ターゲットについて1回分の実行記録しかない。
- 複数回実行による中央値や分散を計算していない。
- ウォームキャッシュとコールドキャッシュを区別していない。
- ネットワーク遅延を独立して測定していない。
- 認証およびAPI通信の時間を独立して測定していない。
- クエリのスケジューリング時間を分離していない。
- アダプターのバージョンが同一ではない。
- 実行エンジンとストレージの配置が異なる。
- 使用したデータは小規模な合成データである。
- クエリ処理コストを分析していない。
- テストをクエリの複雑性別に分類していない。

したがって、この記録は統制されたベンチマークではなく、実装を通じて得られた観察として扱います。

## この記録を掲載する理由

この観察から、次のような、より広い設計上の疑問が生まれました。

> データ量、クエリ特性、実行環境、鮮度要件、運用体制などの条件は、適切なデータパイプライン構成にどのような違いを生むのか。

そのため、この実行時間差は製品比較やアーキテクチャの推奨根拠としてではなく、データパイプライン設計を調査する出発点として使用します。

次のファイルには、実際のコマンド出力から、公開に必要な情報を残した抜粋を掲載します。

- [`bigquery-test-summary.txt`](./bigquery-test-summary.txt)
- [`duckdb-test-summary.txt`](./duckdb-test-summary.txt)

抜粋には、次の情報を残します。

- dbt Coreのバージョン
- アダプターとアダプターのバージョン

- 設定されたスレッド数
- 全体の実行時間
- 成功、警告、エラー、スキップの最終件数

315件すべての個別テストに関する詳細出力は、今回の観察結果を確認するうえで必須ではないため、公開用の抜粋からは省略します。
